# Application survey and HadaMAG profiling

## Decision

**HadaMAG passes the runtime-share gate for a bounded native-Float64 experiment.**
On the local Apple M2, Walsh transforms account for about 79% of complete exact SRE
evaluation time and 85% of the profiled Monte Carlo evaluation time. These are
profiling fractions, not speedups from a new circuit. No H4/H8 replacement was
implemented or timed in this survey.

The arithmetic gate is different: the inspected HadaMAG CPU path explicitly requires
`ComplexF64` states and `Float64` scratch. Neither the reviewed application material
nor these measurements establish a need for 512–4,096-bit arithmetic. Our earlier
Arb/Acb speedups cannot be transferred numerically to this application.

Bayesian clustering is the stronger precision-driven research lead. The published
application reports numerical failure from cancellation, but a runnable author
implementation/input set was not located in this bounded survey. It is a follow-up
data/algorithm investigation, not a ready circuit integration.

## Survey scope and candidates

This pass inspected three concrete applications. Only HadaMAG passed to profiling;
the other two were screened through papers and source availability. This was not
an exhaustive literature review or a performance comparison among applications.

| Candidate | Actual operation and evidence | Fit for the present circuits | Disposition |
|---|---|---|---|
| HadaMAG qubit SRE | Repeated Walsh transforms on products of state amplitudes; public implementation and circuit-state generator | Exact operator match; native Float64, not balls | Profiled; proceed only at native precision |
| Bayesian clustering posteriors / Xpost | Repeated subset convolutions; documented cancellation in fast method | Natural accuracy concern, but zeta/Möbius transforms differ from WHT | Seek runnable input/code and reproduce accuracy issue first |
| DPconv join ordering | Published code plus JOB/CEB query/cardinality data; Boolean fast subset convolution | Inspected fast path uses 32-bit words and different transforms | Reject as an immediate expensive-arithmetic H4/H8 target |

### HadaMAG: an existing scientific computation

The authors' examples evaluate stabilizer Rényi entropy on states generated by
brick-wall circuits of random two-qubit gates. We use that same generator family,
with fixed seeds and saved state vectors. A finite-depth circuit state is not
claimed to be a globally Haar-distributed random state. The publication also
supplies a sampling method and parallel CPU/GPU implementations.
[Application paper, §§4.1–4.2](https://arxiv.org/html/2601.07824v3#S4.SS1)

Pinned source: `bsc-quantic/HadaMAG.jl` at
`68309e74b567c0ee71b80655153c09121c6dfd4e` (2026-04-15).
The exact path calls `compute_chunk_sre(Val(2), ...)`; the sampling path calls
`mc_sre_β!`. Both invoke `call_fht!`. The implementation already reuses real scratch,
prepares shared input arrays, uses XOR masks instead of physical permutations, and
accumulates moments without materializing a full Pauli table.
[SRE source](https://github.com/bsc-quantic/HadaMAG.jl/blob/68309e74b567c0ee71b80655153c09121c6dfd4e/src/SRE.jl)

**Architecture qualification:** the package selects its Julia/LoopVectorization
fallback here. Its packaged FFHT library is x86-only. These results describe the
actual default transform on this ARM machine; they are not measurements of FFHT on
x86, CUDA, MPI, or multithreaded execution.
[Backend selection](https://github.com/bsc-quantic/HadaMAG.jl/blob/68309e74b567c0ee71b80655153c09121c6dfd4e/src/Helpers.jl)

### Bayesian clustering: genuine numerical friction, incomplete application access

Kohonen and Corander compute posterior summaries over clusterings using subset
convolution. They report that floating-point fast subset convolution gave erroneous
results already at 18 items, whereas direct summation was sufficiently accurate in
their experiments. They discuss arbitrary-precision integer arithmetic as a possible
remedy. This is evidence of a real accuracy problem, not evidence that our circuits
solve it. [Original paper, §3.1](https://arxiv.org/pdf/1310.1034)

The author's thesis identifies the implementation as Xpost, written in MATLAB with
C inner loops. Searches of the paper, thesis, author-site route, and indexed code
references did not locate a downloadable implementation or its experiment inputs.
That bounded negative search does not establish that the code is unavailable.
[Author's thesis, §3.2](https://helda.helsinki.fi/server/api/core/bitstreams/a83794d9-8350-4ae9-81d6-992f5e496328/content)

Required competitors would include direct positive summation, sufficient-precision
conventional transforms, and Stoian's FFT-based subset convolution. The latter
provides another algorithmic representation to compare; we have not established
that it meets the desired posterior accuracy at machine precision. H4/H8 do not
directly replace zeta/Möbius transforms. A cancellation-free approach likewise
needs an explicit valid mapping and comparison with prior monotone constructions.
[FFT-based subset convolution](https://arxiv.org/html/2404.18522v1)

### DPconv: concrete data, unsuitable arithmetic for this immediate search

Pinned `utndatasystems/DPconv` at
`dc56bdc52c452bf86b3ac5c224b0176148c38757`. Its repository includes JOB and CEB
query graphs with cardinalities, providing an unusually concrete application/data
pair. [Repository and benchmark instructions](https://github.com/utndatasystems/DPconv)

The inspected `runMinMaxDPconv_instant` reduces to Boolean feasibility, and
`BooleanFSC` / `BoostedBooleanFSC` use `uint32_t` storage with bounded zeta/Möbius
operations. Large input cardinalities do not imply large-integer transform entries.
This is another instance where the application permits a cheaper representation.
It was not built or profiled because it fails the immediate operator/arithmetic
screen. This is not a claim that DPconv admits no useful optimization.
[Transform source](https://github.com/utndatasystems/DPconv/blob/dc56bdc52c452bf86b3ac5c224b0176148c38757/src/include/SubsetConvolution.hpp)

## Measured HadaMAG workloads

All runs use the unchanged package, public APIs, `backend=:serial`, progress off,
one Julia thread, and one BLAS thread. Inputs are saved `ComplexF64` state vectors
from `rand_haar(n; depth, rng=MersenneTwister(seed))`, with depths 2 and 8.

| Workload | Qubits | Complete call, median wall time | Timed FHT share | Uninstrumented sample share |
|---|---:|---:|---:|---:|
| Exact SRE2, two depths | 10 | 4.87–4.90 ms | 79.15–79.22% | 74.42–75.67% |
| Exact SRE2, two depths | 12 | 81.84–82.63 ms | 78.79–78.85% | 79.29–79.96% |
| Exact SRE2, two depths | 14 | 1.369 s | 79.51% | 80.31–80.91% |
| Monte Carlo SRE2, two depths | 16 | 1.268–1.305 s | 84.58–84.70% | 83.97–86.33% |

Exact calls execute respectively 1,024, 4,096, and 16,384 transforms of the
corresponding state-vector length. Sampling calls use 13 beta points, 256 proposals
per beta point, and a fixed sampling seed: 3,341 transforms of length 65,536.
This deliberately bounded sample budget profiles the existing method; its entropy
estimate has not been qualified to a statistical error target. We do not compare
sampling and exact computation as interchangeable accuracy contracts.

The baseline exact outputs had normalization residuals between 1.55e-15 and
9.22e-15. These are diagnostics, not rigorous error bounds on SRE. “Exact SRE” here
means enumeration rather than Monte Carlo; it does not mean exact arithmetic.

## Profiling method and validation

1. Compare the public exact SRE with independent direct Pauli sums for eight small
   cases (2–5 qubits, depths 0/2); all agree within 1e-11, including norm checks.
2. Warm both the original transform dispatch and a timer wrapper calling that same
   transform. The package source and arithmetic remain unchanged.
3. Run five alternating ABBA/BAAB quartets per workload, with original versus timed
   dispatch: **160 complete timed calls**. Assert identical answers for every call
   and the expected transform counts in the instrumented calls.
4. Separately sample uninstrumented execution at a requested 1 ms interval for at
   least 1.5 seconds per workload. Classify a stack as FHT if it includes
   `_fht_julia!`; retain full flat profiles. The eight profiles have 900–1,778 samples.

Time fractions use the median of per-call summed-transform-wall-time / total-call-
wall-time. The wall-time change between instrumented and ordinary medians ranged
from −0.22% to +2.78%; negative values reflect run variability, not negative overhead.
Timers add overhead and sampling includes runtime/GC activity, so the percentages
are approximate. The 10-qubit cases show a roughly 4–5 percentage-point discrepancy
between methods. Both methods clearly exceed the predeclared 20% screening threshold.
No confidence interval or speedup claim is attached to these profile fractions.

State generation, loading, compilation, and warmup are excluded. Allocation and
cleanup inside the public SRE/MC_SRE call are included; garbage collection remains
enabled. Measured allocation per call is about 86 KB, 329 KB, and 1.31 MB for the
three exact sizes and 2.76–2.79 MB for the sampling cases. Other research, compilation,
and analysis were kept separate from the profiling run.

Environment: Apple M2, macOS 26.6.2, local Julia 1.10.10. Julia reports the CPU target
as `apple-m1`, although the hardware reports M2; this is the default runtime setup,
not a specially tuned M2 build. The official Julia archive was checksum-verified
and unpacked only under `.deps`; the Julia depot and environment are also local.
The setup log records an optional CpuId precompile failure on ARM; HadaMAG loaded,
selected its documented fallback, and completed all validation/profiling calls.

## Next step and stopping criteria

**First choice: a small Float64 H4/H8 experiment on captured HadaMAG transform inputs.**
Compare with the package's actual Julia backend and a competent conventional native
butterfly implementation. Preserve SRE accuracy, include scratch/scaling costs,
and validate the complete scientific output before claiming an application win.
The documented custom-transform hook offers an integration point.

A hypothetical 10% transform-time reduction at the measured fraction would save
about 8% of exact-call time. This is an opportunity estimate; our existing ball
results do not predict a 10% native-precision gain. Scaling instructions, SIMD
efficiency, and memory behavior may eliminate the arithmetic advantage entirely.
Stop this branch if it cannot beat the stronger ordinary implementation. A win
only against the ARM fallback must be labeled architecture-specific until tested
against FFHT or comparable baselines elsewhere.

**Second choice: reproduce the clustering cancellation problem on actual likelihood
tables.** Obtain public or reconstructed, clearly labeled application inputs and
an accuracy reference before implementing a new circuit. Stop if the conventional
accurate approach is already cheaper or no compatible construction is found.

Neither route currently establishes a competitive application of a distinctive new
OpenAI/sister-project construction. An H4/H8 success would directly use the older
Alman–Rao non-rigidity circuits; the current theory project remains the discovery path.
